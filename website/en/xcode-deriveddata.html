Developer storage

You can delete DerivedData, but the cost is not zero

It contains build intermediates and code indexes. Deleting it loses no source code, configuration or shipped build. What it does cost you is a noticeably slower next build and a full index rebuild, which is why code navigation feels broken for a while. Know that before you decide.

How to delete itWhen not to

Understand it first

What is actually inside DerivedData

The default location is ~/Library/Developer/Xcode/DerivedData, with one directory per project named after the project plus a hash.

Build: the compiled intermediates

Object files, module caches, link output and the built .app. This is what lets Xcode recompile only part of your project after a one-line change.

Index: the code index

It powers “jump to definition”, “find references” and completion. It does not affect compilation, but the first use after deleting it is slow.

Logs and build records

Small in size, but the only trail you have when a build fails for a reason nobody can reproduce.

Why one project has several directories

The hash encodes the Xcode version and build path. After a major Xcode upgrade or a project move you get another one, and the old one never disappears on its own.

Weigh the cost

Check these before you delete

Short version: if you just want the space back, delete it. If you are about to build or debug, wait.

What you lose: nothing

Source code, Package.swift, Podfile, .xcconfig, asset files, archived releases and committed code are all unaffected — none of them live in DerivedData.

What you pay: one full build

Every source file is compiled again. Minutes on a small project, and on a large project with many Swift files or CocoaPods dependencies it can be considerably longer. Incremental builds resume afterwards.

What you pay: an index rebuild

Until the index is rebuilt, code navigation and completion are unavailable. Xcode does this in the background when you reopen the project. It is the most noticeable part and the one people forget.

When not to do it

Right after a build when you are about to run tests, while profiling with Instruments, while breakpoint debugging, or before a demo. Also quit Xcode first so it is not writing while you are deleting.

Doing it

Three options with very different results

Decide which outcome you want first, then pick the method.

1. See how large it is

du -sh ~/Library/Developer/Xcode/DerivedData

2. Clear only the current project's products, keeping the index

# In Xcode: Product → Clean Build Folder (Shift + Cmd + K)

3. Clear the cached data of every project (indexes rebuild)

rm -rf ~/Library/Developer/Xcode/DerivedData/*

The difference: Clean Build Folder touches only the current project, keeps the index and frees the least space. Emptying the whole directory frees the most, but every project rebuilds its index the next time you open it. Note that rm -rf deletes permanently and does not use the Trash, so check the path before running it — the segment before that trailing /* must be DerivedData/.

A common trap

If your DerivedData is not in the default location

Some people move it next to the project via Xcode → Settings → Locations → Derived Data. When that is the case:

  • The default ~/Library/Developer/Xcode/DerivedData may be empty, which makes it look like Xcode uses no space
  • The space is actually in your custom directory, and that is where you have to clean
  • Cleaners only handle the default location and skip custom paths — deliberately, so they never delete something inside a project directory

Confirming the location first is far less work than hunting for a backup afterwards.

FAQ

About DerivedData

Will deleting it affect my project?

Not the project itself. Source code, dependency declarations, configuration files and archived releases are not in DerivedData. The project builds normally afterwards, just with a full build the first time.

Do I need to run pod install again?

No. Dependency sources and the Pods directory are not inside DerivedData. The next build recompiles those dependencies but does not reinstall them.

Why did Xcode get slow after I deleted it?

It is rebuilding the index in the background after you reopen the project. Until that finishes, jump-to-definition and completion may be slow or inaccurate, then they recover.

Can I just use Xcode's built-in clean instead?

You can, but the result differs. Clean Build Folder clears only the current project and configuration and keeps the index, which is the conservative option. Freeing all the accumulated history requires dealing with the whole DerivedData directory.

Could a cleaner delete my source directory by mistake?

No. The default DerivedData parent is ~/Library/Developer, entirely separate from project directories. The app only operates inside an explicit allowlist, and re-checks the path, directory type and symbolic links before deleting.
