macOS storage

System Data is 100 GB, and it is not a folder

You see a huge “System Data” block in About This Mac → Storage, then search Finder and cannot find it anywhere — because it is a category, not a directory. Understanding that is the difference between a real cleanup and deleting the wrong thing.

Start with the likely sourcesMeasure it yourself

Understand it first

System Data is a category, not a block of disk

macOS sorts your disk into categories: Applications, Documents, Photos, Music, Mail, System Data. The first few have clear owners, and anything left over is swept into System Data.

It is a mixture, not a thing

Device backups, VM disk images, developer caches, logs, mail attachments, local snapshots, index databases. Their only shared property is not belonging anywhere else.

So there is no “clear it” button

No folder named System Data exists. Any tool claiming one-click removal of it is really deleting some specific paths inside, which is why the path list matters.

It grows from normal use

Back up an iPhone once, pull a few Docker images, build a few large projects, and over a few months it quietly reaches tens or even hundreds of gigabytes.

The number is an estimate

The system assigns files to known categories first and everything remaining accumulates here. It can jump around, so do not read too much into small changes.

Ordered by likelihood

The usual suspects, biggest first

Roughly ordered by how much space they take and how often they are overlooked. You rarely need to check all of them — the first two usually explain it.

① iPhone and iPad backups

At ~/Library/Application Support/MobileSync/Backup. Every time you sync or back up an iPhone on this Mac, a full device backup is kept — often tens of gigabytes each, and several per device. This is the single most likely item to pass 100 GB.

How to handle it: in Finder, open Go → Library while holding Option to reach the directory, or manage device backups more safely in System Settings → General → Storage. After deleting, the next backup of that device is a full one again.

② VM and Docker disk images

Docker Desktop, OrbStack, Parallels and UTM each keep a disk image that keeps growing. They share one property: the image only grows, even after you delete things inside the container.

How to handle it: run docker system prune -a first to drop unused images and build cache, then shrink the disk image from Docker Desktop settings. The path varies by version — usually under ~/Library/Containers/com.docker.docker/Data/vms. Verify before deleting anything there.

③ Xcode and developer caches

The whole ~/Library/Developer tree can land in this category: old simulator runtimes, build caches, device support files. Note that Xcode/Archives is your release history and must not be deleted.The five Xcode locations →

④ Local snapshots (APFS)

Without an external backup drive, Time Machine stages restore points on the Mac itself. Large files you deleted may still be pinned by a snapshot, which is why space sometimes does not come back. Check with tmutil listlocalsnapshots /.

⑤ Mail attachments and streaming caches

Mail clients download attachments locally, and Apple Music, Podcasts, the TV app and your photo library keep caches too. Usually a few gigabytes each and rarely the main cause, but they add up.

Do it yourself

Three commands that locate the source

All of them only read, none delete. The first is the important one: sort every subdirectory of your Library by size and the biggest offender is right there.

1. The largest items in your Library (biggest last)

du -sh ~/Library/* 2>/dev/null | sort -h | tail -15

2. Check whether local snapshots are holding space

tmutil listlocalsnapshots /

3. Size of your device backups specifically

du -sh ~/Library/Application\ Support/MobileSync/Backup

If the first command shows a directory of tens of gigabytes, that is almost certainly it. If nothing looks large yet System Data is still huge, the answer is more likely local snapshots or a VM disk image — neither of which du accounts for properly, so use the second and third approaches instead.

Safety boundary

What is safe to remove and what is not

  • Safe: old simulator runtimes, build caches, device support files, app caches and logs, device backups you no longer need
  • Safe: unused Docker images and build cache via docker system prune -a, rather than deleting image files directly
  • Safe: older local snapshots via sudo tmutil deletelocalsnapshots; current files are unaffected
  • Leave alone: ~/Library/Developer/Xcode/Archives — your release archives and symbols
  • Leave alone: your photo library, files in iCloud, chat data, Keychain, and any Library subdirectory you do not recognise

One rule covers the rest: before deleting a directory you do not recognise, confirm it is regenerable. A name that sounds like a cache is not proof that it is one.

About this tool

It covers part of this, not all of it

Mac Space Cleaner handles app caches, developer tool caches and the three Xcode locations, and shows Downloads, iCloud Drive, WeChat chat data and WPS backups as read-only. It does not handle iPhone backups, Docker images, local snapshots or your photo library — use the native methods above for those. FAQ

About System Data

Why can I not find System Data in Finder?

Because it is not a folder. It is a statistical category in About This Mac → Storage. macOS groups everything that is not Applications, Documents, Photos, Music or Mail into it, so it is assembled from many unrelated paths.

I deleted a lot of files but free space did not change. Why?

A local snapshot is probably pinning the space. Run tmutil listlocalsnapshots / to check. This is common on Macs with no external backup drive that have had Time Machine enabled at some point.

Does System Data shrink by itself?

Partly. macOS thins older local snapshots and some caches when space runs low. Device backups, VM disk images and accumulated Xcode runtimes are not in that group and will not disappear on their own.

Is a one-click “clear System Data” tool safe?

It depends entirely on which paths it deletes. This category contains your device backups, chat data and photo library, so a tool that does not distinguish contents is risky. Locating the specific source first is the safer route.

Can a web page scan my Mac?

No. A browser cannot read your local disk structure. The commands on this page have to be run by you in Terminal, and anything that needs a real local scan must be done by a native app you download and run.
