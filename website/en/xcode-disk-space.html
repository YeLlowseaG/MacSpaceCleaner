Developer storage

How much Xcode takes is really five different numbers

“Xcode is using too much space” is not one problem. It is five locations with completely different properties: four of them can be regenerated, and one is your release history, which you cannot get back. Measure them separately before you delete anything.

How to measure itJump to the verdict

Break it down

The five locations Xcode storage comes from

The first four live under ~/Library/Developer, completely separate from your project directories. The fifth is Xcode itself.

1. Simulator runtimes

At CoreSimulator/Profiles/Runtimes. Each one is a full system image, typically 4–9 GB. Old versions are never removed automatically, which makes this the largest block.

2. Build cache (DerivedData)

At Xcode/DerivedData. Build intermediates and indexes. The more projects you have and the longer you build, the bigger it gets — and it only grows.

3. Device support files

At Xcode/iOS DeviceSupport (plus watchOS, tvOS and visionOS). One set per physical device and OS version you have connected. People who change phones accumulate these fastest.

4. Archives ⚠️ never delete

At Xcode/Archives. The archive of every build you shipped, including dSYM symbols. This is a record, not a cache.

5. Simulator devices and shared cache

CoreSimulator/Devices holds the simulators you created; CoreSimulator/Caches/dyld is a regenerable linker cache.

Plus: Xcode itself

In /Applications, usually in the low tens of gigabytes. It is the tool you use every day and is not part of any cleanup.

One by one

Which can be deleted, and what it costs

There is only one criterion: can it be regenerated, and how long does that take?

Simulator runtimes — safe

Keep the newest version of each platform, keep others only if you need them. Deleted runtimes can be downloaded again from Xcode Settings → Components, at the cost of a few gigabytes of download. This is the single biggest win.How to decide which →

DerivedData — safe

Deleting it loses no source code, configuration or shipped build. The cost is a noticeably slower next build while indexes and intermediates are rebuilt. Do not do it the moment after a build if you are about to run tests.DerivedData explained →

Device support files — safe

These are symbol files Xcode pulled from a device when you debugged on it. Deleting them means the next connection to that device re-fetches them, which takes a few minutes. If you are actively debugging that specific device with Instruments or crash logs, you will wait for the re-fetch.

Archives — do not delete

This holds the build you submitted and its dSYM symbols. Delete it and crash logs from those versions can no longer be symbolicated, and the same build cannot be re-uploaded. It is not regenerable, and no cleaner should count it as reclaimable space.

Simulator devices and the dyld cache — safe

Devices are ones you created, so deleting them resets simulator state. The dyld shared cache rebuilds on demand and only makes the first simulator launch slower. Neither affects installed runtimes.

Measure first

One command, all five numbers

Run this in Terminal. It only reads, deletes nothing, and sorts the output from smallest to largest so the biggest offender is last.

Size of each location

du -sh ~/Library/Developer/Xcode/* ~/Library/Developer/CoreSimulator/* 2>/dev/null | sort -h

Watch three names in particular: DerivedData, iOS DeviceSupport and Profiles/Runtimes. On a tight development machine these three are usually the bulk of it.

Then deal with the largest one first, confirm Xcode and your projects still behave, and only then move to the second. Deleting everything at once saves a few minutes, but if a project depends on a particular old runtime you will have a hard time working out which one.

Order of operations

If you only clean once, do it in this order

  • First: old simulator runtimes — biggest win, lowest risk; keep the newest per platform
  • Second: DerivedData — usually gigabytes to tens of gigabytes; accept one slow build
  • Third: device support files — delete only the versions for devices you no longer own
  • Fourth: the dyld shared cache — smallest win, always rebuilds
  • Never: Archives — the space you save is not worth your release history

FAQ

About Xcode disk usage

How much does Xcode usually take?

It depends on how many simulator runtimes you have and how much build history. Xcode itself is around 10–15 GB. Once you have several iOS and watchOS runtimes and a few months of builds, the whole ~/Library/Developer directory is commonly tens of gigabytes, and most of it is regenerable.

Which part should never be deleted?

~/Library/Developer/Xcode/Archives. It holds the archive of every build you shipped, including dSYM symbols. Once gone, crash logs from those versions cannot be symbolicated and the same build cannot be re-uploaded. It is a release record, not a cache.

Will deleting these break Xcode?

The regenerable parts will not. Runtimes can be downloaded again, DerivedData and the shared cache rebuild automatically, and device support files are re-fetched the next time that device connects. The cost is time, not data.

Why does my DerivedData keep growing?

It only grows. Every configuration change, every SDK version and every simulator architecture can leave its own intermediates behind, and Xcode does not clean up by default. After a couple of major Xcode upgrades it is often the largest single item.

Does cleaning touch my project files or source code?

No. All five locations live under ~/Library/Developer and /Applications, separate from your project directories. The app only operates inside an explicit allowlist of paths and never touches project files.
